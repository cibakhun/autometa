# AutoMeta

Eine Suche für Gebrauchtwagen aus vielen Fahrzeugbörsen: Suchkriterien einmal eingeben, Angebote aus verschiedenen Quellen in einer einheitlichen Liste vergleichen und per Klick zur Originalanzeige springen.

**Stand:** Phase 2. Echte Angebote kommen von AutoScout24, Kleinanzeigen, Quoka, Autohero und auto.de (siehe „Quellen“). Ohne eingeschaltete Quellen zeigt die Seite generierte Demo-Daten und sagt das oben auch.

## Schnellstart

Voraussetzungen: Node.js 22 und eine Postgres-Datenbank (lokal per Docker oder Supabase).

```bash
npm install
cp .env.example .env.local      # DATABASE_URL anpassen, falls nötig
docker compose up -d            # lokale Postgres-Datenbank (optional)
npm run db:setup                # Schema anlegen, Marken/Modelle/PLZ laden, Demo-Daten importieren
npm run dev                     # http://localhost:3000
```

## Befehle

| Befehl | Zweck |
| --- | --- |
| `npm run dev` | Entwicklungsserver |
| `npm run db:migrate` | SQL-Migrationen aus `supabase/migrations` anwenden |
| `npm run db:seed` | Marken- und Modellliste sowie bekannte Postleitzahlen schreiben |
| `npm run db:prepare` | `db:seed`, solange die Datenbank keine Angebote hat die Demo-Daten importieren, Schadenshinweise alter Angebote nachtragen, Marktwerte und Reparaturschätzungen berechnen (läuft bei jedem Start) |
| `npm run ingest -- autoscout24 kleinanzeigen` | Quellen einmal importieren, danach Dubletten neu gruppieren und Marktwerte berechnen (`demo` für Demo-Daten) |
| `npm run worker` | Hintergrund-Job: importiert und prüft die Quellen aus `SCRAPE_SOURCES` alle `SCRAPE_INTERVAL_MINUTES` Minuten (je höchstens `SCRAPE_RUN_MINUTES`), baut nebenher die Mängelprofile aus RDW-Daten und verschickt alle `ALERT_INTERVAL_MINUTES` Minuten die Benachrichtigungen |
| `npm run defects` | Ein Lauf der Mängelprofile (sonst macht das der Worker), danach die Risikopuffer neu |
| `npm test` | Tests; mit `TEST_DATABASE_URL` auch gegen eine echte Datenbank |
| `npm run lint` / `npm run typecheck` / `npm run build` | Prüfungen wie in der CI |

## Aufbau

```
supabase/migrations/   Datenbankschema (läuft auf Postgres und Supabase)
src/core/              Datenmodell, Marken-/Modellliste, Normalisierung, Geo-Funktionen
src/ingest/            Adapter-Schnittstelle, Import-Lauf, Dubletten, Segmente, Migrationen, Seed
src/ingest/adapters/   ein Adapter je Quelle (autoscout24, kleinanzeigen, quoka, autohero, autode, demo), Einzelprüfung listing-check
src/ingest/http/       PoliteFetcher (Abstand, robots.txt, Abbruch bei Sperren), HTML-Helfer
src/search/            Filter aus der URL lesen, SQL-Suche, PLZ-Auflösung, Suche in eigenen Worten (natural.ts)
src/profiles/          Profile ohne Anmeldung (Geräte, Codes), Merkliste, Suchaufträge
src/alerts/            Web Push (VAPID, Versand) und der Benachrichtigungs-Job
src/app/               Next.js-Seiten: Suche, Detailseite /angebot/[id], Weiterleitung /go/[id], API /api/search
scripts/               Kommandozeilen-Einstiege für Migration, Seed, Import, Worker und Start
data/                  Postleitzahlen mit Koordinaten (GeoNames, CC BY 4.0)
```

So fließen die Daten: Adapter ruft ab → Rohdaten landen in `raw_listings` → Normalisierung auf das einheitliche Format → `listings`. Jede Quelle wird in einem eigenen Lauf importiert (`ingest_runs`); zwei Läufe derselben Quelle können sich nicht überschneiden. Nach jedem Import gruppiert `updateDuplicates` dasselbe Fahrzeug auf mehreren Börsen (gleiche Marke und Modell, keine widersprüchliche Leistung, Kraftstoff oder Getriebe, dazu eine von drei Regeln): (1) Ort und Monat der Erstzulassung bekannt: gleicher Monat, km ±2 %, Preis ±8 %, höchstens 25 km entfernt. (2) Eine Börse nennt nur das Baujahr (Quoka, Autohero; `listings.first_registration_year_only`, die Seiten zeigen dann nur das Jahr): gleiches Jahr, sonst wie (1), erst ab 1.000 km. (3) Eine Börse nennt keinen Ort (Autohero, auto.de): gleiches Jahr (und Monat, wo beide ihn kennen), Kilometerstand auf den Kilometer gleich, ab 1.000 km und kein runder Hunderter, Preis ±15 %, weil auto.de für dasselbe Auto bis zu rund 13 % mehr verlangt als der Händler selbst. Treffer nach (2) und (3) zählen nur, wenn sie eindeutig sind: Hat eines der beiden Angebote auf der anderen Börse noch einen zweiten Kandidaten, wird nicht geraten. Die Suche zeigt das Fahrzeug einmal, zum günstigsten Preis, mit „Hier am günstigsten von N Börsen · auch bei …“ und dem Aufpreis je Börse; die Detailseite listet alle Börsen und sagt, wenn eine andere günstiger ist.

Danach berechnet `updateMarketValues` (`src/ingest/market.ts`) für jedes aktive Angebot einen Marktwert: den Median der Preise vergleichbarer intakter Angebote (gleiche Marke und gleiches Modell, Erstzulassung ±1 Jahr, km ±25 % oder mindestens ±15.000 km, gleicher Kraftstoff und gleiches Getriebe, Leistung ±20 %), dazu die mittlere Hälfte als übliche Spanne. Vergleichbar sind aktive und in den letzten 90 Tagen verschwundene Angebote ab 500 € ohne Schadenshinweis und ohne abgelaufene HU, jedes Fahrzeug nur einmal. Unter 5 vergleichbaren Angeboten gibt es keinen Wert. Es sind Angebotspreise, keine Verkaufspreise. Schadenshinweise liest `detectDamage` (`src/core/damage.ts`) aus dem Titel („Motorschaden“, „Getriebe defekt“, „springt nicht an“, „Unfallwagen“, „für Bastler“ …), verneinte und reparierte Schäden („kein Rost“, „Motorschaden behoben“) zählen nicht. Die Suche filtert danach („Zustand laut Titel“). Schnäppchen (`src/core/deal.ts`): Jeder Marktwert bekommt eine Verlässlichkeit (`market_confidence`): verlässlich ab 20 vergleichbaren Angeboten, deren mittlere Hälfte höchstens 40 % des Marktwerts umfasst, brauchbar ab 10 und 60 %, sonst unsicher. `deal_pct` ist, wie viel Prozent ein Angebot ohne Schadenshinweis unter einem verlässlichen oder brauchbaren Marktwert liegt; ab 50 % darunter gilt es als auffällig billig (live fast immer Betrug, Leasingübernahme, Teile oder ein Schaden, den der Titel nicht nennt), bekommt eine Warnung und zählt nicht als Schnäppchen. „Bestes Schnäppchen“ (`sort=below_market`) sortiert danach, der Filter `deal=10|20|30` verlangt mindestens so viel Prozent, auch in Suchaufträgen. Die „Empfehlung“ gibt auffällig billigen Angeboten −30 und unsicheren Marktwerten 0 Preispunkte. Jede Preisänderung eines Angebots landet per Trigger in `listing_prices`. Die Detailseite zeigt daraus den Preisverlauf (wie oft gesenkt oder erhöht, insgesamt um wie viel, Stufenlinie, jede Änderung; `src/core/price-history.ts`) und unter „Online“, wie lange das Angebot schon online ist: ab dem Datum der Börse, wo eine Prüfung es gelesen hat (Kleinanzeigen), sonst ab dem ersten Sehen durch AutoMeta als Mindestdauer. Die Suche filtert mit „Preis gesenkt“ (`gesenkt=3|7|30|ja`: letzte Preisänderung war eine Senkung, in so vielen Tagen) und sortiert mit „Zuletzt im Preis gesenkt“ (`sort=price_drop`); Karten zeigen eine Senkung der letzten 14 Tage (bei diesem Filter jede) als Badge „Preis −500 €“.

Flip-Bewertung: Der Reparaturkatalog (`src/core/repairs.ts`, Seite `/reparaturen`) beschreibt rund 55 typische Arbeiten mit Stunden für einen Hobbyschrauber, Schwierigkeit 1 bis 5 und Teilepreisen für die Kompaktklasse; alle Werte sind Schätzungen. Jeder Schadenshinweis führt zu Arbeiten (Motorschaden → Gebrauchtmotor, Kupplung → Kupplungssatz …), dazu Aufbereitung und bei abgelaufener HU die HU-Vorbereitung; die Fahrzeugklasse aus Leistung, Typ und Marke skaliert die Teilepreise. `updateRepairEstimates` (`src/ingest/repairs.ts`) speichert für jedes aktive Angebot mit Schadenshinweis Teile, Stunden, Schwierigkeit, Sicherheit und ob es abgeschleppt werden muss. Die Marge rechnet `calculateFlip` (`src/core/flip.ts`): Marktwert × (1 − Verhandlungsabschlag) − Kaufpreis − Teile − Nebenkosten (HU, Zulassung, Abholen oder Abschleppen), geteilt durch die Stunden ergibt den Stundenlohn. Dieselbe Formel steht in SQL für die Sortierungen „Flip: höchster Stundenlohn“ und „Flip: höchste Marge“ und die Filter „Schwierigkeit bis“ und „Flip-Marge ab“. Abschlag, Nebenkosten, Level und Mindestmarge stellt jeder unter `/einstellungen` ein (Cookie im Browser, keine Konten); `/flip` öffnet die Suche mit diesen Werten. Auf der Detailseite rechnet der Flip-Rechner mit änderbaren Werten nach.

Risikopuffer und Modell-Akte (Phase 3): Von der Marge geht ein Risikopuffer ab, gespeichert in `repair_risk_hidden_eur` und `repair_risk_unclear_eur`. **Versteckte Mängel:** `src/ingest/defects` zieht je Modell und Altersgruppe (5–7, 8–10, 11–13, 14–17, 18–25 Jahre) über die offizielle API der niederländischen Zulassungsbehörde RDW (opendata.rdw.nl, CC0) eine Stichprobe von 300 zugelassenen Autos mit gültiger HU und zählt, welche bei der APK der letzten 24 Monate einen Mangel hatten, je Baugruppe (Bremsen, Rost, Fahrwerk …; Zuordnung der niederländischen Mängelnamen in `src/core/defect-codes.ts`). Gespeichert werden nur diese Zählungen (`model_defect_profiles`). Puffer = Anteil mit Mangel × übliche Teilekosten aus dem Katalog, ohne Baugruppen, die die geplante Reparatur abdeckt; ohne Profil zählt der Durchschnitt gleich alter Autos. **Unklarer Schaden:** Bei Hinweisen ohne Ausmaß (Unfall, springt nicht an, Defekt …) gilt ein schlimmerer Fall (`SEVERE_CASES` in `src/core/repairs.ts`) ab 30 % unter Marktwert als zunehmend wahrscheinlich, ab 70 % als sicher. Die Detailseite zeigt die Modell-Akte mit Mängelquoten gegen den Durchschnitt, Schwachstellen und Links zu Forum, ADAC und Videos (nur Links). Der Worker baut die Profile nebenher: höchstens `RDW_MAX_REQUESTS` Abfragen pro Lauf (Standard 600, `RDW_MIN_DELAY_MS` Pause, Standard 2 s, robots.txt wie bei den Börsen), stündlich weiter, solange Profile fehlen, sonst täglich; Profile älter als 90 Tage werden erneuert. `RDW_PROFILES=false` schaltet das ab. Stand und letzter Fehler stehen auf `/reparaturen`.

Karosserie: Was die Börse liefert (auto.de) oder der Titel nennt („Variant“, „Combi“, „Turnier“, „Active Tourer“ als Van, „Kasten“ als Sonstige …, `detectBodyType` in `src/core/normalize.ts`), sonst die übliche Karosserie des Modells (`src/core/body-types.ts`, Golf als Limousine wie bei den Börsen; nur der BMW 2er hat keine). Gespeicherte Angebote bekommen sie einmal je `BODY_RULES_VERSION` im Worker (`src/ingest/body-review.ts`), neben der ersten Runde.

Suche in eigenen Worten: Das Feld über den Ergebnissen nimmt einen Satz wie „zuverlässiger Kombi für Familie bis 8.000 €“. `/ki?text=…` liest ihn mit festen Regeln (`parseNaturalSearch`, `src/search/natural.ts`, keine KI-API, kostet nichts pro Suche) und leitet auf die normale Suche mit den passenden Filtern um; der Satz geht als `ki` mit, damit die Seite zeigt, was verstanden wurde, was es nicht als Filter gibt („sparsam“, Farbe, Vorbesitzer) und welche Wörter unbekannt waren. Erkannt werden Marke und Modell (auch „Octavia“ ohne Marke, „320d“ als 3er, „Peugeot 2008“), Preise („bis 8k“, „zwischen 6.000 und 9.000 €“, „ca. 10.000 €“), Kilometer, Baujahr und Alter, PS/kW, Kraftstoff, Typ, Getriebe, Anbieter, Börse, TÜV/HU, Zustand, Flip-Wünsche („zum Flippen“, „Marge ab 1.000 €“, „einfach zu reparieren“), PLZ oder Ort mit Umkreis („um München“, Ortsnamen aus `postal_codes`, `findTown`) und Verneinungen („kein Diesel“). „Familie“ heißt Kombi, Van oder SUV, wenn kein Typ genannt ist; Ausstattungs- und Ausführungswörter (GTI, Standheizung) landen im Suchbegriff, der jetzt jedes Wort einzeln im Titel sucht. Sortiert wird nach Flip bei Schadens- oder Flip-Wünschen, sonst nach „Empfehlung“: je Prozent weniger HU-Mängel als gleich alte Autos laut Modell-Akte ein Punkt (höchstens ±50), je Prozent unter Marktwert ein Punkt (höchstens ±30, Angebote mit Schadenshinweis −30), Unbekanntes zählt 0. „zuverlässig“ blendet dazu Angebote mit Schadenshinweis aus. Bei dieser Sortierung zeigt jede Karte den Vergleich aus der Modell-Akte.

Tägliche Prüfung: Jedes Angebot soll einmal am Tag geprüft werden, also in der Liste der Börse wieder gesehen oder auf seiner eigenen Seite bestätigt (`last_seen_at`, in der Suche als „geprüft …“, auf der Detailseite als „Zuletzt geprüft“). AutoScout24 liest dafür seinen ganzen Bestand jeden Tag einmal durch (siehe unten). Kleinanzeigen und Quoka lassen per robots.txt nur ihre neuesten Seiten lesen; dort prüft jeder Lauf nach den neuesten Seiten für den Rest seiner Zeit Angebote, die seit 20 Stunden nicht gesehen wurden, einzeln auf ihrer eigenen Seite (`checkListings`, `src/ingest/adapters/listing-check.ts`), die am längsten ungeprüften zuerst. Gespeichert wird davon nur das Ergebnis, nie die Seite (dort stehen Beschreibung und Name privater Verkäufer). Bei Kleinanzeigen liest die Prüfung einer bestätigten Anzeige außerdem den Preis aus dem Preisfeld (`#viewad-price`, ohne durchgestrichenen alten Preis) und das Datum darunter (`#viewad-extra-info`, als `listings.listed_on`, das früheste gewinnt) und die Fahrzeugdaten aus dem Detailkasten der Anzeige (`.addetailslist--detail`: Kraftstoffart, Getriebe, Leistung, Fahrzeugtyp, HU bis, Fahrzeugzustand) samt „Privater“ oder „Gewerblicher Nutzer“ aus dem Verkäuferkasten (`kleinanzeigenVehicleFacts`). Diese Werte wählt der Verkäufer aus Listen der Börse; sie ersetzen, was der Titel ergab, nur ein im Titel genanntes HU-Datum und ein im Titel genannter Schaden bleiben, und „Beschädigtes Fahrzeug“ zählt als Schaden nur bei einem sonst intakten Auto. Zeigt die Liste das Angebot später wieder nur mit Titel, bleiben Kraftstoff, Getriebe, Leistung, Verkäuferart und ein genanntes HU-Datum stehen. Das Log jeder Prüfung nennt, wie viele Seiten Fahrzeugdaten hatten (bei 0 hat sich vermutlich die Seite geändert). Was nicht genau in der erwarteten Form dasteht, bleibt weg. Zeigen in einer Gruppe von 25 Prüfungen mehr als 10 Seiten einen anderen Preis als gespeichert, gilt der Preis als falsch gelesen und die Gruppe ändert keinen. 404/410, eine Weiterleitung weg von der Anzeige oder der Hinweis „gelöscht“/„nicht mehr verfügbar“ der Börse (nicht im Text des Verkäufers) heißt verkauft; trägt die Seite die Nummer der Anzeige, ist sie bestätigt; Unklares bleibt, wie es ist, und kommt erst einen Tag später wieder dran (`checked_at`). Sagt eine Gruppe von 25 Prüfungen fast nur „weg“, glaubt der Lauf ihr nicht und hört auf (dann antwortet die Börse vermutlich anders als erwartet). Sperrt die Börse eine Anzeigenseite (401/403/429, Captcha), geht in diesem Lauf keine Anfrage mehr hinaus; was die Listen gezeigt haben, zählt trotzdem, und der Lauf vermerkt „Einzelprüfung abgebrochen“. Der Hinweis über der Suche zeigt je Börse, wie viel Prozent ihrer Angebote in den letzten 24 Stunden geprüft wurden (`sources.checked_24h`, nach jeder Runde gezählt), `/admin/quellen` zeigt dazu die älteste Prüfung, wie viele Angebote in 24 Stunden aus welchem Grund raus sind und wie weit der AutoScout24-Durchlauf ist.

Merkliste, Suchaufträge und Benachrichtigungen: Es gibt keine Konten. Wer zum ersten Mal etwas speichert, bekommt ein Profil; der Browser hält dafür einen zufälligen Schlüssel im Cookie `autometa_profil`, die Datenbank nur dessen SHA-256-Hash (`profiles`, `profile_devices`, `src/profiles/store.ts`). Ein zweites Gerät nutzt dasselbe Profil über einen Code von `/geraete` (8 Zeichen, 30 Minuten gültig, einmal verwendbar); was es vorher allein gespeichert hatte, wandert mit. Das Herz an jedem Angebot setzt es auf die Merkliste (`favorites`, Seite `/merkliste`, mit Preis beim Merken). „Suche speichern“ über den Ergebnissen legt die aktuelle Suche als Suchauftrag ab (`saved_searches`: Filter und Sortierung als Query-String, dazu die Flip-Einstellungen, weil Margenfilter und Flip-Sortierung davon abhängen; wer sie unter `/einstellungen` ändert, ändert sie auch für alle Suchaufträge seines Profils). `/suchauftraege` zählt je Suchauftrag, was seit dem letzten Öffnen neu oder günstiger ist; „Neue ansehen“ öffnet die Suche mit `seit=<Zeitpunkt>`. Neu heißt: zuerst nach diesem Zeitpunkt gesehen, und keine Börse hatte dasselbe Fahrzeug (Dublettengruppe) schon vorher; günstiger heißt: Preis seitdem gesenkt (`listings.price_dropped_at` und `price_before_drop_eur`, gesetzt per Trigger bei jeder Preissenkung, bei einer Erhöhung wieder geleert).

Benachrichtigungen kommen per Web Push (Standard der Browser, ohne bezahlten Dienst): Der Browser meldet sich beim Push-Dienst seines Herstellers an, AutoMeta speichert dieses Abo (`push_subscriptions`, nur mit Adressen der bekannten Push-Dienste von Google, Mozilla, Apple und Microsoft, `PUSH_SERVICE_HOSTS`) und schickt verschlüsselte Nachrichten dorthin. Das nötige VAPID-Schlüsselpaar erzeugt die App beim ersten Bedarf selbst und legt es in `app_keys` ab (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` gehen vor). Der Service Worker `public/sw.js` zeigt die Nachricht und öffnet beim Antippen die passende Seite. Auf dem iPhone geht das nur, wenn AutoMeta über „Teilen → Zum Home-Bildschirm“ als App geöffnet ist (ab iOS 16.4, dafür gibt es `manifest.webmanifest` und die Icons). Der Worker ruft alle `ALERT_INTERVAL_MINUTES` (Standard 5) den Job `runAlerts` (`src/alerts/run.ts`) auf: Für jeden Suchauftrag mit eingeschalteter Benachrichtigung sucht er, was in den letzten 48 Stunden und nach dem Speichern (oder Einschalten) neu oder günstiger wurde und noch nicht gemeldet ist, und schickt eine Nachricht mit Anzahl und den ersten drei Autos. Gemeldete Fahrzeuge merkt er sich drei Tage (`saved_search_hits`), so kommt ein Auto, das erst am Ende einer Importrunde passt (etwa weil der Flip-Filter erst mit dem Marktwert greift), trotzdem, und keins doppelt, außer sein Preis sinkt erneut. Bei der Merkliste meldet er Preissenkungen gegenüber dem zuletzt gemeldeten (oder beim Merken gültigen) Preis und Anzeigen, die verschwunden sind. Nachtruhe (Standard an, je Profil): Zwischen 22 und 7 Uhr geht nichts raus, um 7 Uhr kommt es gesammelt. Lehnt der Push-Dienst ein Abo als unbekannt ab (404/410), wird es gelöscht; andere Fehler versucht der nächste Lauf erneut. `ALERTS=false` schaltet den Job ab.

Wann ein Angebot aus der Suche verschwindet (`listings.gone_reason`, `gone_at`):

- Liest ein Adapter den ganzen Bestand (`fullSnapshot`), zählt jedes fehlende Angebot als verpasst. Liest er nur Teile, zählen Fehlende nur in den Teilen, die er vollständig gelesen hat (`completedSegments`). Nach zwei verpassten Läufen hintereinander gilt ein Angebot als verkauft (`missed`).
- Sagt die eigene Seite des Angebots, dass es weg ist, verschwindet es sofort (`checked`).
- Ein Angebot, das `staleAfterDays` Tage weder gesehen noch bestätigt wurde, verschwindet ebenfalls (`stale`): bei AutoScout24 nach 3 Tagen, bei allen anderen nach 2. Ob es verkauft ist, wissen wir dann nicht; die Detailseite sagt das so, und für die Standzeit im Marktwert zählt es nicht.
- Taucht es wieder in einer Liste auf, ist es wieder in der Suche.

Der Bot hält die robots.txt jeder Börse ein (Entscheidung vom 15.11.2026). Gespeichert werden nur Fakten, keine Beschreibungen, Fahrgestellnummern oder Namen privater Verkäufer. Fotos werden nie kopiert: Von jedem Angebot merkt sich AutoMeta nur die Adresse des Vorschaubilds, das die Börse selbst in ihrer Liste zeigt, und zwar nur, wenn es auf dem Bildserver der Börse liegt. Der Browser lädt das Bild direkt von dort. Liefert die Börse es nicht aus, steht ein Platzhalter da. Hat ein Angebot kein Bild, ein Duplikat desselben Fahrzeugs auf einer anderen Börse aber schon, wird dessen Bild gezeigt. Bestehende Angebote bekommen ihr Bild, sobald ein Lauf sie wieder sieht. TÜV/HU: Keine Börse nennt das HU-Datum in ihrer Ergebnisliste als eigenes Feld (auch Kleinanzeigens eigenen TÜV-Filter verbietet die robots.txt). AutoMeta liest es deshalb aus dem Titel („TÜV 05/2027“, „HU bis 5.27“, „TÜV neu“, „2 Jahre TÜV“, „HU abgelaufen“, `src/core/inspection.ts`). „Neu“ zählt ab dem ersten Fund 24 Monate. Steht nichts im Titel und ist das Auto jünger als 3 Jahre, gilt die erste HU 36 Monate nach der Erstzulassung, aber nur bei mindestens 3.000 €, einer Erstzulassung nicht nach dem aktuellen Monat und, wenn die Kilometer bekannt sind, höchstens 10.000 km pro Monat seit der Erstzulassung (sonst ist es Zubehör in der Autorubrik oder ein vertipptes Datum). Der Filter „TÜV/HU“ zeigt nur Angebote mit bekanntem Datum. Such- und Ankaufanzeigen („Suche Golf 7“, „Ankauf aller Fahrzeuge“) und Leasingübernahmen fallen bei Kleinanzeigen und Quoka weg. Marke und Modell werden auch hinter ein paar einleitenden Wörtern erkannt („2023 Skoda Superb“, „Verkaufe Polo“). Hat eine Börse ihr Seitenformat geändert, bricht der Lauf mit einer klaren Meldung ab, statt leere Daten zu speichern, und legt die Seite unter `/admin/quellen` ab. Quoka und Autohero werden ohne feste CSS-Klassen gelesen (`src/ingest/http/cards.ts`): Jeder Link auf eine Anzeige markiert einen Eintrag, Preis, Kilometer, Erstzulassung, Kraftstoff und Ort werden an ihrer Form erkannt („12.990 €“, „98.000 km“, „03/2019“, „10115 Berlin“). Das übersteht die meisten Umbauten einer Börse.

Tempo: Alle Quellen laufen gleichzeitig, jede höchstens `SCRAPE_RUN_MINUTES` (Standard 50) von jeder Runde aus `SCRAPE_INTERVAL_MINUTES` (Standard 60); der Rest der Runde gehört Dubletten, Marktwerten und Reparaturschätzungen. AutoScout24 wählt seinen Abstand selbst: so kurz, dass alle Bereiche in `SCRAPE_CYCLE_HOURS` (Standard 24) einmal gelesen sind, berechnet aus den zuletzt gemeldeten Trefferzahlen, aber nie unter `SCRAPE_MIN_DELAY_MS` (Standard 2 s, im Deployment 1 s über `nixpacks.toml`) und nie über 5 s. Bei rund 740.000 Angeboten (37.000 Seiten, Stand 23.11.2026) reicht selbst 1 s nur knapp: ein Durchlauf dauert dann etwa 1,1 Tage, mit 2 s etwa 1,5 Tage. Reicht die Untergrenze nicht, dauert der Durchlauf länger als einen Tag; `/admin/quellen` zeigt das. Kleinanzeigen und Quoka fragen alle 3 Sekunden (rund 15 Minuten neueste Seiten, danach rund 35 Minuten Einzelprüfung, also etwa 550 Anzeigen pro Runde und Börse), Autohero und auto.de alle 5 Sekunden (300 Seiten, rund 25 Minuten). Keine Börse nennt in ihrer robots.txt ein `Crawl-delay` für alle Bots (Stand 21.11.2026); nennt eine eines, gilt das längere. Mit `AUTOSCOUT24_MAKES`, `KLEINANZEIGEN_MAKES` und `QUOKA_MAKES` lassen sich die Marken eingrenzen (Slugs wie `volkswagen,bmw`).

## Eine neue Quelle anbinden

1. Datei in `src/ingest/adapters/` anlegen, die `SourceAdapter` aus `src/ingest/adapter.ts` erfüllt (`fetch` liefert Rohdaten, `normalize` bringt sie ins einheitliche Format).
2. In `src/ingest/adapters/index.ts` registrieren.
3. `npm run ingest -- <quelle>` ausführen.

Regeln für jeden Adapter:

- Nur Fakten speichern (Marke, Modell, Preis, km, Erstzulassung, Ort). Keine Beschreibungstexte und keine Fotos kopieren; die Adresse des Vorschaubilds aus der Liste darf als `imageUrl` mit, geprüft mit `sourceImageUrl(adresse, "<bildserver-domain>")`.
- Keine Namen oder Kontaktdaten privater Verkäufer speichern.
- Niemals Bot-Schutz, Captchas oder Logins umgehen.
- Jedes Angebot verlinkt auf die Originalanzeige.

Zusätzlich für Scraper (Quellen ohne Schnittstelle):

- Webseiten nur über `PoliteFetcher` aus `src/ingest/http/fetcher.ts` abrufen. Er nennt sich ehrlich (`SCRAPE_USER_AGENT`), wartet zwischen zwei Abrufen bei derselben Börse (je Quelle eigener Abstand, nie unter `SCRAPE_MIN_DELAY_MS`, das selbst mindestens 1 Sekunde sein muss; längeres `Crawl-delay` gewinnt), hält die robots.txt ein (`SCRAPE_RESPECT_ROBOTS`) und begrenzt jeden Lauf auf `SCRAPE_RUN_MINUTES` Minuten und `SCRAPE_MAX_REQUESTS` Abrufe.
- Meldet eine Börse 401, 403 oder 429, zeigt ein Captcha oder leitet auf eine Anmeldung um, bricht der Lauf sofort ab (`BlockedError`). Das gilt auch, wenn schon die robots.txt so antwortet. Nicht erneut versuchen, keine anderen IPs oder Browser-Kennungen.
- Weiterleitungen folgt der Fetcher selbst (höchstens 5). Jeder Schritt zählt als eigener Abruf, wartet seinen Abstand ab und muss von der robots.txt seines Hosts erlaubt sein.
- `kind: "scrape"` setzen und `fullSnapshot: false`, solange der Adapter nicht wirklich den ganzen Bestand liest. Sonst würden nicht gelesene Angebote fälschlich als verkauft markiert.

## Deployment (Coolify über AgencyOS)

AutoMeta läuft wie die anderen AgencyOS-Projekte als Coolify-App, die AgencyOS beim Anlegen des Projekts erstellt hat: Branch `main`, Nixpacks, Port 3000.

- **Build:** `nixpacks.toml` legt wie bei AgencyOS Node 22, `npm ci`, `npm run build` und `npm run start` fest. Der Build braucht keine Datenbank.
- **Datenbank:** eine PostgreSQL-Ressource im selben Coolify-Projekt. Ihre interne URL kommt als `DATABASE_URL` in die Umgebungsvariablen der App, in Coolify oder im AgencyOS-Projekt.
- **Start:** `npm run start` führt die Migrationen aus, schreibt Marken, Modelle und PLZ und importiert die Demo-Angebote, solange die Datenbank noch keine Angebote hat. Danach startet Next.js und, wenn `SCRAPE_SOURCES` gesetzt ist, daneben der Import-Worker. Schlägt ein Schritt vor dem Start fehl, startet der neue Container nicht und die alte Version läuft weiter. Ein Terminal oder ein Pre-deployment command ist nicht nötig.
- **Ausrollen:** den Pull Request in AgencyOS mit „Merge to Main“ zusammenführen und danach unter „Deployments“ ein Deployment starten. AgencyOS legt die App ohne GitHub-Webhook an, ein Push auf `main` allein rollt also nichts aus, solange in Coolify keiner eingerichtet ist.
- **Domain:** die automatische sslip.io-Adresse ist von außen nicht erreichbar. Für eine öffentliche Adresse eine Subdomain in Cloudflare (proxied) auf den Server zeigen lassen und dieselbe Adresse bei der App als Domain eintragen.
- **Echte Angebote:** `nixpacks.toml` setzt für das Deployment `SCRAPE_SOURCES=autoscout24,kleinanzeigen,quoka,autohero,autode`, der Worker läuft also nach jedem Ausrollen ohne weiteren Schritt. Ein eigener Wert für `SCRAPE_SOURCES` in den Umgebungsvariablen der App in Coolify geht vor (zum Beispiel nur `autoscout24`). Der Worker läuft im selben Container, importiert sofort und dann alle `SCRAPE_INTERVAL_MINUTES` Minuten (Standard 60). Stürzt er ab, startet ihn der Container neu, die Website läuft davon unabhängig. Sobald eine echte Quelle Angebote geliefert hat, löscht der Import die Demo-Daten. Die Logs der App zeigen jeden Lauf (`[autoscout24] …`, `duplicates: …`).

- **Quellen-Status:** Mit `ADMIN_TOKEN` (mindestens 16 Zeichen, in den Umgebungsvariablen der App) zeigt `/admin/quellen?token=<ADMIN_TOKEN>` je Quelle die aktiven Angebote, den letzten Lauf mit Fehlermeldung und die letzten Läufe. Ohne `ADMIN_TOKEN` antworten alle `/admin`-Adressen mit 404.
- **Testabruf vom Server:** Auf derselben Seite lässt sich eine Seite der bekannten Börsen (AutoScout24, Kleinanzeigen, Quoka, Autohero, auto.de, pkw.de) über den Server abrufen, auf Wunsch mit den eigenen Skripten der Seite. Es gelten dieselben Regeln wie beim Import (robots.txt, Abstand, Abbruch bei Sperren). Die Antwort wird in `scrape_samples` gespeichert (die neuesten 80) und lässt sich als Text lesen, mit `&grep=` nur um die Treffer herum. So sieht man, was eine Börse unserem Bot wirklich schickt, bevor man einen Adapter baut oder repariert.

Alternativ funktioniert jede andere Postgres-Datenbank, zum Beispiel Supabase. Dort kann die App den gepoolten Connection-String (Transaction-Modus, Port 6543) nutzen. Migrationen brauchen aber eine direkte Verbindung oder den Session-Modus (Port 5432), weil sie eine Sperre über mehrere Transaktionen halten. Dafür `MIGRATION_DATABASE_URL` setzen. Mit Port 6543 bricht `db:migrate` absichtlich ab. Dasselbe gilt für den Import-Worker: Er sperrt jede Quelle über eine Sitzungs-Sperre und braucht deshalb eine direkte Verbindung oder den Session-Modus. Auf Coolify ist die interne Postgres-URL direkt, dort passt alles.
